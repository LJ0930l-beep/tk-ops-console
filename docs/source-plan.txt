一、结论先行：一共 26 张表
按「TikTok Shop 多店铺运营」的完整业务来设计，一共 26 张表：业务表 20 张 + 系统支撑表 6 张。
不需要一次建完：一期 19 张就能让团队用起来（商品、订单、达人、视频全打通）；二期加 5 张做直播、投放和利润核算；库存 2 张只在没有 ERP 管库存时才建。

三条设计要点（决定这套表好不好用）

[TABLE]
要点 1：订单明细是全系统的「交汇点」。
成本从 SKU 经映射表来，带货来源从达人 / 视频 / 直播来，实际到账从结算流水来——所有账都在订单明细这一层对上。所以明细里要冻结成本快照（以后改成本价不影响历史利润）；匹配不上内部 SKU 的订单行必须报警，绝不能按 0 成本算，否则利润会虚高。
 |  |

[/TABLE]

[TABLE]
要点 2：达人一人一档，建联 / 合作 / 寄样都是流水。
同一个达人全公司只有一条档案（按 @用户名去重），谁认领归谁，保护期内没进展自动退回公海。这是解决 BD 撞单、互相抢达人、员工离职带走资源 的根本办法；每一次联系、每一次寄样都留痕，BD 绩效和达人 ROI 都从流水里自动算出来。
 |  |

[/TABLE]

[TABLE]
要点 3：「预估」和「实际」分开记，不互相覆盖。
订单上的金额是预估，结算流水是平台实际打款。运营看日报用预估（快），老板看利润以结算为准（准）；两个口径同时存在、可以逐单对账。另外，时间统一存 UTC，报表按站点时区或北京时间切日——口径开工前定死，否则每天的数字对不上。
 |  |

[/TABLE]

二、这套后台管什么、给谁用
适用对象：在 TikTok Shop 上经营一个或多个店铺（跨境店或本土店、单站点或多站点），靠「达人带货 + 自营短视频 / 直播 + 广告投放」出单的团队。
一句话定位：把分散在卖家中心、Excel、微信群里的店铺、订单、达人、视频、直播和钱，收进一个后台，按人、按店看清楚——谁在干活、哪条内容在卖货、到底赚没赚钱。

五、26 张表逐一说明（字段级）
每张表按「用途 → 数据来源 → 字段清单」写。字段列的是业务上必须有的，开发时可在此基础上细化。

[TABLE]
以下约定对所有表生效，下文不再重复：
① 每张表都带 5 个公共字段：id（主键）、created_by（创建人）、created_at（创建时间）、updated_at（更新时间）、is_deleted（删除标记——删除只打标记，不真删）。
② 金额统一 DECIMAL(18,2) 并带币种字段；汇总时按汇率表折算人民币。
③ 说明里的「→某表」表示关联到那张表；平台单号、@用户名等外部编号都建唯一索引，重复同步不会产生重复数据。
 |  |

六、四条核心业务流程
下面四条流程说明这些表是怎么「串起来」干活的。
6.1 达人带货闭环：找达人 → 出单 → 算 ROI
BD 在「达人公海」搜索或导入达人，认领后进入自己的私海，开始计算保护期。（达人库）
每联系一次记一条跟进，约好下次跟进时间，到点提醒。（建联跟进表）
谈妥后建合作单：合作方式、佣金率、坑位费、约定条数和截止日；坑位费一键生成待付款费用。（合作单表、费用表）
仓库按合作单寄样、填物流单号；签收后开始计时，超过约定天数没出内容，自动提醒 BD 催。（寄样表）
达人发布后，BD 贴视频链接，系统自动解析视频 ID 并挂到这张合作单下。（视频表）
联盟订单同步进来，按视频 ID / 达人自动归到对应合作。（订单明细表）
系统自动算 合作投产比 = 带货净 GMV ÷（样品成本 + 寄样运费 + 坑位费 + 达人佣金），按达人、按 BD 出排行。
6.2 订单到利润：每一单到底赚多少
同步程序每 15～30 分钟按「更新时间」增量拉订单，写入订单表和订单明细表，同时写一条同步日志。
订单明细按平台 SKU ID 经映射表找到内部 SKU，冻结成本快照；找不到的进「待映射」清单，并在工作台提醒。
售后同步进来后，冲减对应订单的收入和达人业绩。
每日同步结算流水，用平台实际扣掉的佣金、运费、达人佣金替换预估值。
单笔利润 = 结算实收 − 成本快照 − 分摊广告费 − 分摊其他费用（坑位费、仓储等），全部按汇率表折人民币。
利润报表可按店铺 / SKU / 达人 / 月份切换；还没结算的订单用预估值，并单独标注「预估」。
6.3 直播：排班 → 开播 → 复盘
运营按周排班：选直播账号、主播、场控、计划时段、主推商品。（直播场次表，状态 = 已排班）
开播前一天提醒主播和场控。
下播后同步或导入本场数据：场观、最高在线、成交单数、GMV；投流花费从广告日报汇总过来。
主播填写复盘；系统出主播时长、场均 GMV、千次观看成交额等排行。
6.4 数据同步与告警：保证数据不悄悄断
同步任务按「店铺 × 数据类型」执行，每次写一条同步日志：时间段、拉到几条、新增 / 更新 / 失败几条。
每次拉取的时间窗口前后重叠几分钟，靠平台单号去重——宁可多拉，不能漏单。
同步失败、店铺授权快到期、或「平时每天有单、今天 0 条」时，立即推送告警到企业微信 / 飞书群。
接口凭证加密保存，只在服务器端使用，不出现在页面和日志里。

八、权限设计
权限分三层，全部在后台配置，不用改程序：
菜单 / 按钮权限：按角色配置能进哪些页面、能不能新增 / 修改 / 删除 / 导出。（角色表）
数据范围：全部 / 本组 / 仅本人 / 指定店铺。（角色表 + 数据权限表）
敏感字段：成本价、利润、达人联系方式、坑位费单独授权，没有权限的人看到的是「＊＊＊」。

8.2 几条硬规则
BD 离职时，主管一键把他的私海达人、合作单转给别人，客户资源不流失。
删除只打标记不真删；改成本价、改达人归属、改费用、导出数据，全部写操作日志，任何人不能改日志。
导出默认关闭，按角色开通；每次导出都记录是谁、导了什么。
九、技术架构与部署
前端：Vue 3 + Element Plus 管理后台，电脑浏览器使用；BD 记跟进、主播填复盘等高频小操作做手机适配。
后端：Java（Spring Boot）或 Python（FastAPI），定时任务负责数据同步与告警。
数据库：MySQL 8，按本方案 26 张表建库；每天自动备份，保留 30 天。
部署：建议阿里云香港（或新加坡）服务器——访问 TikTok 接口更稳定，免 ICP 备案，国内浏览器直接打开；起步 2 核 4G 即可。
归属：服务器开在贵司自己的云账号下，数据和源码归贵司。
告警：同步失败、授权快到期、备份失败，推送到企业微信 / 飞书群。
